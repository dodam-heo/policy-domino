# 정책도미노 — 제출용 아키텍처와 검증 계약

## 목적
법률·시행령·시행규칙·고시·훈령·예규·지침과 자치법규의 **공식 변경 사건**으로부터, 그 조항이나 기준을 실제 활용하는 **공공부문** 제도·사업·서비스의 변경 영향을 도출한다. 민간조직 제외. 변경된 법 자체를 다시 변경하라는 권고를 생성하지 않는다.

## 하나의 실행·출판 경로

```
GitHub Actions: policy-domino.yml (단일 정기 수집·배포)
  └── policy_domino.__main__
      ├── engine.collect_index / official_api   공포·변경 이력 수집
      ├── engine.events / semantic_diff          공식 동일 법령 신구 대조
      ├── engine.relationships / dependents      변경 조항의 실제 인용·적용 검증
      ├── engine.pipeline                        공식 원천 증빙 스냅샷
      ├── public_services                        Gov24 공개 사업 운영기준
      ├── engine.publication                     단일 기관 영향 결과 생성
      │     ├── agency_actions                    직접 규율 대상기관
      │     └── impact_scope                      확인된 연결 범위
      ├── ai_impact                              출처 제한 LLM 업무 검토
      └── site/templates/agency.html             단일 템플릿·공통 에셋
                ↓
      site/classic/data.json (한 개의 공개 데이터 계약)
      /impact/ 및 /classic/ (동일 데이터에 대한 URL 별칭)
                ↓
      GitHub Pages 1회 배포
```

`--source official`은 실시간 공식 API를 사용한다. `--source stored`는 공식 원천 증거를 저장한 현재 수집 상태로부터 동일 파이프라인을 재구성하며, 과거 UI 버전의 결과는 사용하지 않는다. 저장된 원문 캐시는 허용하지만 v2 등의 과거 영향 분석 카드를 최종 데이터에 합치는 호환 계층은 두지 않는다.

## 핵심 데이터 경계
1. **정책 변경 사건**: 발령기관(`issuing_authorities`), 변경 문서(`source_documents`), 공포·시행일, 공식 원문, 실제 변경 조항·전후 본문(`article_differences`), 그 내용에서 파생된 간명한 `change_summary`.
2. **의존관계**: 해당 사업·하위 규정이 실제 변경 조항을 인용하거나 변경된 명명된 기준에 구체적인 적용비율·산식을 사용하는 근거. 제목이나 담당부처 유사성만으로 연결하지 않는다.
3. **기관별 검토사항**: 실제 사업·기관 이름과 역할, 변경 조항 및 사업 공식 기준, 필요한 조치, 출처, 반영 상태(별도 증빙 없는 완료·미조치 추정 금지).
4. **금액 범위**: `comparison_scope=source_policy_only`인 전후 값은 상위 정책의 기준값이다. 사업 자체의 최종 금액이 아니다. 각 사업의 가구 수·적용비율·반올림 규칙이 확인되지 않으면 사업별 계산값은 표시하지 않는다.

## 수집 정확성
당일과 최근 7일의 법령·행정규칙·자치법규 전 종류를 중첩 수집하고, 기본 최근 10년을 순환 탐색한다. 실패·불완전한 공식 API 수집 구간은 추적하여 재시도한다. 출처 미확보는 '변경 없음'이 아니며, 모든 사건을 분석 완료했다고 주장하지 않는다.

## AI의 실제 적용 범위
LLM은 공식적으로 확인된 기관별 업무 변화와 검토 과제의 서술을 생성한다. 모델을 바꿀 수 있도록 API 호출 계층은 분리한다. AI가 새 법령·기관·금액·완료 여부를 만들어 공식 결과를 덮어쓰지 못하게 하고, 결과는 근거 지문으로 검증한다. **수집된 모든 변경으로부터 모든 영향을 AI가 독립적으로 발견하는 단계는 현재 구현되지 않았으므로 시연·문서에서 완성됐다고 표시하지 않는다.**

## UI 정보 순서
1. 누가 발령했는지 / 어떤 법적 문서를 바꿨는지
2. 실제 변경 조항·정책 내용 및 신구 비교
3. 실제 변경 조항과 연결된 법령·규정
4. 영향받는 공공기관·사업의 필터 및 상세 조치
5. 기관별 근거·시행일·반영 상태, 검증된 AI 의견

## 회귀 검증
공식 수집 이력의 완전성·실패 재시도, 개정 조문 비교, 유사명 오연결 차단, 동시 개정·실제 인용 관계, 발령기관 분리, 상위금액의 사업금액 오표시 금지, 기관별 필터·상세 화면 렌더링, 단일 배포 경로 및 레거시 재유입 차단을 자동 테스트한다.

## 누락 없는 공식 원천 탐색·검증 상태

`official_api`와 `collect_index`는 기관·분야·지원사업명으로 필터링하지 않습니다. 법제처 공식 목록의 일자별 법령·행정규칙·자치법규 전체(행정규칙의 현행·연혁 포함)를 수집하며, 공식 법령 변경이력은 보조 검증 경로입니다. 날짜·출처·현행/연혁별 `coverage` 항목은 완전/부분실패 상태를 기록합니다.

`data/v4_state.json`은 파생된 화면 카드가 아닌 **공식 문서ID와 버전·인덱스·실제 조회 원문·상세 처리·재시도 이력의 지속 상태**입니다. 초기 누락을 줄이기 위해 기본 10년 범위의 28일 구간을 순환 수집하고, 매번 당일 포함 8일간의 모든 종류를 추가 조회하며, 불완전한 API 응답을 성공으로 간주하지 않습니다. 기간 범위는 설정할 수 있고, 범위 밖의 기존 공식 기록은 삭제하지 않습니다. 재검증되지 않은 과거 UI 버전 메타데이터는 공식 수집으로 인정하지 않습니다.

정식 본문이 아직 확보되지 않은 **공식 API 인덱스 기록**은 `official_index_only`로 파생 화면에 표시할 수 있으나, 법령 변경 내용이나 기관·사업 파급을 사실로 생성하지 않습니다. 별표 다운로드 링크는 수치 원문 대조와 구분해 저장하며, PDF/HWPX 텍스트 추출이 불가능한 첨부는 `unresolved_attachments`로 남겨 다음 실행에서 다시 시도합니다. 이는 누락된 표를 추측으로 채우는 경로가 아닙니다.

`source official`은 `dori`를 기본 DRF 식별자로 사용하며 실제 공식 조회 성공 여부로 수집 상태를 판별합니다. 단순히 식별자 문자열이 있다고 수집 성공으로 판정하지 않습니다. `source stored`는 보관된 증거로부터 동일한 화면 계약을 재현하되 신규 수집을 성공했다고 주장하지 않습니다.

### 회귀 테스트
- 일반적인 모든 규정 종류의 날짜 범위 탐색, 현행/연혁 구분, 페이지 수집의 완료/실패 이력
- 동일 범위 재수집 후 문서의 누적·중복 방지 및 공식 출처 승격
- 실제 상세 조회에 실패한 문서의 재시도와 이전 정상 증거 유지
- 연도별 고시의 신구 문서 대응(제정 표시도 포함)
- 별표 PDF/HWPX 원문 확보 및 추출 불가의 정직한 상태
- API 인증 누락 시 파일·화면을 새로운 공식 수집 성공으로 위장하지 않기
